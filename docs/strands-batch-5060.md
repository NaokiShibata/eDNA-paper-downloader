# RTX 5060 TiでStrandsの5問一括処理を比較

2026-10-09に、同じ論文・質問で5回の順次HTTP要求と1回の5問一括要求を比較した。
今回の40件では標準の一括処理が約7%遅く、順次処理を維持する判断となった。
長い抄録では高速化したが、通常サイズの抄録で追加コストを回収できなかった。
本番設定とコードは変更していない。

## 条件

- GPU: 物理GPU 1、RTX 5060 Ti、16,311 MiB、driver 595.84。
- モデル: `StrandsAgents/strands-decider-2B-hobson-v19`、revision `bb282d786bc251fd4e3068de3ada9ddbb38127cd`。
- 実行環境: strands-decider 0.1.0、PyTorch 2.13.0 / CUDA 12.9、Transformers 5.18.0。
- 質問: 現在の `edna-macrofauna-v6`、scope / actual_use / microbial_only / method_relevance / study_typeの5問。
- 入力: ローカルの `results/edna_latest.csv` 5,405件から先頭10件、seed 5060の無作為25件、抄録の長い順に5件を選択。
- 選択データSHA-256: `055ea9ab146970e034faf21b657dd93df3cab6b014ecb37d0723935a92a1ad1a`。
- 通常の入力整形を使用し、抄録は最大6,000文字、先頭75%・末尾25%に制限。
- 各サーバー条件で両方式をウォームアップし、論文ごとに順次→一括と一括→順次の実行順を交互にした。
- 完了結果キャッシュは無効。各条件を1周測定。サーバー起動・モデルロード・ウォームアップは時間に含めない。

専用サーバーはport 8013を使用した。
GPU 0の既存Strandsサーバーは変更せず、Clef 27Bはこの比較で呼び出していない。
GPU 1にはデスクトップのメモリ使用もあり、完全な専有状態ではない。

## 結果

| サーバー条件 | 送信方法 | 平均秒/件 | 中央値秒/件 | 40件のHTTP合計秒 | 順次とのラベル差 |
|---|---|---:|---:|---:|---:|
| 共通部分キャッシュ有効（標準） | 5問順次 | 0.700 | 0.581 | 28.01 | — |
| 共通部分キャッシュ有効（標準） | 5問一括 | 0.748 | 0.727 | 29.93 | 1/40 |
| 共通部分キャッシュ無効 | 5問順次 | 0.696 | 0.571 | 27.83 | — |
| 共通部分キャッシュ無効 | 5問一括 | 1.149 | 1.008 | 45.97 | 0/40 |

全160回の論文評価でHTTP・推論エラーは0件。
キャッシュ無効の一括処理は順次より約65%遅かった。
サーバー再起動前後の順次処理の最終ラベルは40件すべて一致した。

| 入力群 | 標準の順次 秒/件 | 標準の一括 秒/件 | 一括による時間変化 |
|---|---:|---:|---:|
| 先頭・無作為の35件 | 0.575 | 0.724 | 約26%増加 |
| 抄録の最長5件 | 1.573 | 0.921 | 約41%短縮 |

最長5件はすべて元の抄録が6,000文字を超え、入力整形で切り詰められた。
今回の意図的に長い入力を含む標本での平均を、全件の速度として一般化しない。

`nvidia-smi`で約0.2秒ごとに観測したGPU全体のメモリ最大値は、標準条件で5,962 MiB、キャッシュ無効条件で8,188 MiBだった。
順次と一括を同じプロセス内で交互に実行したため、PyTorchが保持する割り当てとデスクトップ使用分を含む。
方式ごとの独立した必要VRAMや瞬間的な最大値を示す測定ではない。
観測範囲では16 GiBに収まり、OOMは発生しなかった。

## 判定差

300文字未満の抄録では除外を`unsure`にする既存ガードを集計時に適用した。
標準の順次処理は`in_scope` 2件、`out_of_scope` 10件、`unsure` 28件。
標準の一括処理はそれぞれ2件、9件、29件だった。

1件の差はmethod_relevanceの確率が順次0.5986、一括0.6011となり、除外条件の0.6をまたいだためだった。
この論文は順次では`out_of_scope`、一括では`unsure`となり、現在の二段階構成では一括のときだけ27Bへ渡る。
標準条件での全確率の最大絶対差は0.0097、キャッシュ無効条件では0.0101だった。
一括処理で確率が完全に一致するとは扱わない。
独立した正解ラベルによる精度評価は行っておらず、判定差が改善か悪化かは未確定。

## 実装上の理由と判断

標準の一括経路はタイトル・抄録の共通部分を一度計算し、そのモデルキャッシュを5問分に展開して質問を評価する。
順次経路は各問の全入力を個別に評価する。
キャッシュを無効にした一括経路は全入力を5行に複製し、最長質問に合わせてパディングする。
HTTPを5回から1回に減らしても、モデル内部の実行経路と計算量が変わるため、高速化は保証されない。
短い入力では共通部分を再利用する利点が小さく、今回の測定では一括経路全体の追加時間が上回った。
共通部分が長い入力だけでは再利用の効果を確認できた。

入力を4096トークンの上限まで切り詰める場合、一括は最長質問に合わせて共通部分の長さを決める。
順次では質問ごとに入力の残せる長さが変わるため、数値演算以外にも判定差が生じうる。
今回の一括方式をそのまま既定にすることは推奨しない。
長い抄録だけ一括にする切り替えは候補だが、文字数による最適な境界と判定差を追加検証してから判断する。
Strands→27B全体の短縮時間とRTX 8000での効果は、この測定では未検証。

## 検証サーバーの起動

この環境では最初の推論が`Cannot find ptxas-blackwell`で失敗した。
検証用プロセスだけにインストール済みCUDA 13.1のコンパイラを指定して解消した。
モデル・ライブラリ・本番サーバーの設定は変更していない。

```bash
TRITON_PTXAS_BLACKWELL_PATH=/usr/local/cuda-13.1/bin/ptxas \
  pixi run python script/serve.py --preferred-gpu 1 --port 8013
```

キャッシュ無効条件では、GPU選択とコンパイラ指定を維持して直接起動した。

```bash
CUDA_VISIBLE_DEVICES=1 TRITON_PTXAS_BLACKWELL_PATH=/usr/local/cuda-13.1/bin/ptxas \
  pixi run strands-decider serve StrandsAgents/strands-decider-2B-hobson-v19 \
  --device cuda --host 127.0.0.1 --port 8013 --no-prefix-cache
```

一次モデルの一括送信は既存の`first_stage_batch_questions`で切り替えられる。
この検証では二段階全体を実行せず、同じ`evaluate_abstract`に一次モデルのみを指定し、`batch_questions`を切り替えた。
検証専用サーバーは測定後に停止した。
入力・登録情報・生スコア・GPU観測記録は無視対象の`benchmark/clef/strands-batch-5060*/`に保存し、commit・pushしない。
